# Технический аудит Gallery Grid

**27 ноября 2026 года · develop · 892b2d3 · общая оценка 7,3/10.**

Gallery Grid выполняет основную задачу персональной фотостены. В браузере работают смена кадров, часы, архив и просмотр увеличенного изображения. Проверки кэша, ротации и API воспроизводятся локально. По сравнению с предыдущим аудитом (5,7/10) восстановлены lint и CI, появились 38 тестов, пагинация архива и обработка отказов внешних сервисов. Самая срочная задача — ротация исторически раскрытого ключа OpenWeather. Следующая по отдаче — уменьшение объёма каталога, который браузер получает при каждом открытии фотостены.

## 1. Назначение, стек и архитектура

| Область | Что реализовано |
|---|---|
| Среда | Node.js 24.21.0, npm 11.19.0, lockfile, Next.js 16.4.6, Turbopack, React и React DOM 19.2.4, TypeScript 5.9.3 в строгом режиме. |
| Интерфейс | App Router, серверные страницы в `app/`, клиентские компоненты в `components/`, глобальный CSS, локальный Titillium Web и внешняя таблица стилей Font Awesome. |
| Страницы | Главная — сетка до 9 фото с обновлением раз в 30 с. Cloud Grid — 12 фото, Time Grid — 10 фото плюс часы и дата, Small Grid — отдельный источник Picsum. Все три обновляются раз в 15 с. Архив `/list` — по 60 фото. `/gallery` показывает только облачную часть. |

| Инфраструктура | Vercel с командой `npm run build`. GitHub Actions на push и PR в develop/main, Node 24, `npm ci`, lint, тесты и сборка. Права workflow ограничены чтением содержимого, checkout не сохраняет credentials. |
| Сосуществующие версии | Активная реализация в `app/`, обслуживаемые статические файлы в `public/`. **Путь кадра.** Сервер объединяет встроенные URL с результатом Admin API, создаёт адреса превью и передаёт данные клиенту. Клиент выбирает кадры, предварительно загружает следующее фото и завершает замену после перехода или тайм-аута. Основная модель ротации отделена от React и проверена на видимые дубли, период до повторного показа, изменение размера и отказ загрузки. Часовой интервал учитывается в рамках экземпляра фотостены. Small Grid использует собственную колоду.

**Границы ответственности.** Отдельные модули каталога, погоды, пагинации и ротации соответствуют масштабу приложения. Основные точки связанности — передача полного серверного объекта изображения в клиент, поиск открытого диалога через CSS-селектор и совмещение двух видов переходов в GalleryGrid. Для дальнейшей разработки достаточно локальных изменений. Оснований для разделения на сервисы не выявлено.

**Неприменимо.** В проекте нет собственной БД, схемы, индексов, транзакций, пользовательских аккаунтов и пула соединений с БД. Dockerfile и оркестрации контейнеров нет. Запуск и завершение HTTP-сервера делегированы Next.js и хостингу. Приложение не создаёт отдельного постоянно работающего серверного процесса.

### Надёжность, ресурсы и развёртывание

- Холодный отказ Cloudinary оставляет на объединённых страницах встроенный каталог. При ошибке фонового обновления сохраняется последний успешный результат. Настоящий пустой ответ кэшируется. Проверены сбой на второй странице и восстановление, отсутствующие ключи, режимы папок и границы префикса webhook. Ревалидация с профилем max помечает запись устаревшей, обновление происходит при последующем использовании. [Next.js revalidateTag](https://nextjs.org/docs/app/api-reference/functions/revalidateTag)
- Погода загружается после рендера, обновляется раз в 15 минут и отменяет устаревший запрос при смене города. Повторный вызов с тем же городом может обслуживаться серверным кэшем. Ошибка погоды локальна для виджета.
- Таймеры и подписки основных компонентов снимаются при размонтировании. Кэш статических файлов SW ограничен 80 записями, страницы ограничены списком маршрутов. Навигация использует сеть с резервной копией, запросы с query и API обходят кэш. Офлайн для второй страницы архива и самих внешних фотографий не гарантируется. В коде загрузки оригинала есть отдельный путь удержания памяти, см. ниже. Долгий профиль heap, нагрузку CPU и параллельные production-запросы не измеряли.
- В сборке галерея исполняется без секретов. Для боевой среды требуются действительные параметры облака и погоды, если нужны соответствующие интеграции. Контроль квот, доставка webhook и фактическая ревалидация между экземплярами Vercel требуют эксплуатационных данных. Конфигурация CI проверена в Git, статус конкретного удалённого запуска и правила защиты веток не запрашивались.

**Итого 7,3/10**, среднее десяти экспертных оценок с равными весами. Для персональной галереи архитектура оправдана. Самые заметные улучшения уже дали пагинация, изоляция погоды и проверенное поведение при сбое Cloudinary.

1. **Сразу** — закрыть P1 у поставщика и во всех используемых окружениях. Критерий готовности — новый ключ обслуживает погоду, старый отозван, проверены доступные показатели потребления.
2. **Следующая итерация** — уменьшить набор полей фотостены, заменить квадратичную дедупликацию, повторить измерения в тех же условиях. Проверить настройку папки тестовым событием в разрешённом окружении.
3. **После этого** — проверить квоты и пограничные ограничения погоды, добавить управление движением и браузерный сценарий. Сохранить простоту интерфейса фотостены и проверить поведение при отказе изображения.
4. **Планово** — синхронизировать документацию с кодом, исправить манифест, разобрать legacy после проверки потребителей. Масштабные изменения инфраструктуры обосновывать реальными метриками посещений, задержек и трафика.

**Границы вывода.** Аудит охватывает локальный снимок, доступную Git-историю, реестр npm и один браузерный движок. Firefox через snap в среде аудита не запустился, Safari, реальные устройства, экранный диктор и установленная PWA не проверялись. Блокировка внешних хостов позволяет оценить геометрию и HTML, но не качество реальных изображений, CORS скачивания или скорость CDN. Не измерялись продакшен-трафик, счета, Web Vitals, heap под нагрузкой, права сервисных ключей, внешние настройки Vercel и доля покрытия строк. Эвристический поиск секретов не покрывает все форматы хранения. Эти области не включены в число подтверждённых дефектов.
