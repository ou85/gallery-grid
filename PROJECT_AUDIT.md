# Технический аудит Gallery Grid

Снимок проекта: ветка `develop`, коммит `0e78bed`, 26 ноября 2026 года. Общая оценка — **5,7/10**. Галерея собирается и выполняет основную задачу. Наибольшие риски перед дальнейшим развитием связаны с ключом в истории репозитория, кэшем браузера и зависимостью страниц от погоды.

## 1. Назначение, стек и структура

Gallery Grid — публичный фотоархив с автоматически меняющимися сетками, часами, погодой, списком фотографий, просмотром и скачиванием оригиналов. На `/` и `/cloud-grid` работает ротация каталога Cloudinary. `/list` показывает общий каталог, `/gallery` — активы из подключённой папки, `/small-grid` использует Picsum. Существуют PWA-манифест и сервис-воркер. Описание в README в целом соответствует реализации. Уточнения нужны для резервного каталога, обновления кэша и работы webhook.

| Слой | Реализация |
|---|---|
| Приложение и сборка | Next.js **16.4.6** из lockfile, App Router, Turbopack. Все пять страниц динамические. |
| UI | React и React DOM **19.2.4**, TypeScript **5.9.3**, JSX, глобальный CSS, локальный Titillium Web WOFF2 и Font Awesome **5.15.3** с CDN. |
| Пакеты и среда | npm, lockfile v3. Проверено с Node **24.21.0** и npm **11.19.0**. Установленный Next в основном checkout — **16.4.0**. |
| Данные | Cloudinary SDK **2.11.0**, публичный список URL в `images.js`, OpenWeather через сервер, Picsum через браузер. Нет БД, ORM, очередей и пользовательских аккаунтов. |
| Развёртывание | Конфигурация Vercel для Next.js, команда `npm run build`. CI, Docker, описание среды и автоматические тесты в отслеживаемых файлах не обнаружены. |

- `app/` содержит маршруты, metadata, манифест, CSS и два Route Handlers. `components/` отвечает за интерактивность. `lib/` содержит каталог, преобразования URL и клиент OpenWeather. `public/` содержит статические ресурсы и активный service worker.
- `index.html`, `pages/*.html`, `scripts/`, большая часть `styles/`, корневые `manifest.json` и `sw.js`, `pictures/` и `pictures.json.old` относятся к старому статическому приложению. Next.js обслуживает старые адреса перенаправлениями. Из `styles/` используется WOFF2, а `images.js` остаётся источником актуального каталога.
- Сервер загружает метаданные каталога и начальную погоду. Клиент получает сериализованный каталог, перемешивает его и загружает изображения напрямую с CDN. Такая схема подходит небольшому публичному проекту. Основные ограничения роста — полный листинг, передача всего каталога и зависимость от квот поставщиков. Отдельные серверные сервисы или база данных пока не обоснованы.
- Границы server/client в целом ясны. Слабые места — выбор папки продублирован между каталогом и webhook, пауза ротации зависит от CSS-селектора диалога, а один и тот же список одновременно обслуживает серверный вывод и клиентскую ротацию.

## 2. Сильные стороны

- Миниатюры отделены от оригиналов, трансформации Cloudinary имеют фиксированные размеры. Списки используют ленивую загрузку, просмотр — отдельный ограниченный вариант, скачивание — явное действие.
- Для основного каталога есть резервный набор URL, TTL серверных данных и механизм инвалидации. Ротация основных сеток пропускает скрытую вкладку и открытый диалог, таймеры и обработчики удаляются при размонтировании.
- Актуальная погодная интеграция держит ключ на сервере и использует фиксированный upstream. Webhook проверяет подпись, время и применяет сравнение с постоянным временем для корректных буферов.
- Стандартный `dialog`, видимый фокус кнопок просмотра, серверные Open Graph и Twitter Card, единый favicon и перенос старых адресов дают хорошую основу.

## 5. Зависимости, безопасность и эксплуатация

- Все прямые runtime-зависимости имеют активное применение. React DOM нужен Next.js. Cloudinary SDK нужен для Admin API. TypeScript и пакеты типов обслуживают разработку. Замена SDK ручным API увеличит объём поддержки без измеренной выгоды.
- В приложении нет `next/image`. `images.remotePatterns` в конфиге не управляет прямыми запросами обычных `img`. Оптимизация выполняется через URL Cloudinary. Для мобильных вариантов стоит сначала уменьшить ячейки и измерить качество, затем вводить ограниченное число размеров.
- Next-версия зафиксирована и содержит поддержку `experimental.agentUpgrade`. Старые версии React и TS в выводе `outdated` сами по себе не проблема. Прямых зависимостей, подтверждённых как неподдерживаемые, не нашёл. Для сверки статуса Next использована [политика поддержки Next.js](https://nextjs.org/support-policy).
- Секреты действующей интеграции читаются с сервера из env. Публичные Cloudinary URL являются идентификаторами ресурсов. Значения `.env.local` и конфигурацию Vercel не читал. Дедупликация обработки webhook и согласованность кэша при нескольких серверах зависят от платформы. Документация [Next.js о кэшировании при self-hosting](https://nextjs.org/docs/app/guides/self-hosting) и [unstable_cache](https://nextjs.org/docs/app/api-reference/functions/unstable_cache) помогает отделить локальную ревалидацию от гарантий хостинга.
- Backend ограничен адаптерами к внешним API. Индексы, транзакции, пул соединений и логин неприменимы. POST webhook защищён подписью, остальные маршруты публичны по назначению. Собственного долгоживущего сервера и процедур graceful shutdown нет, жизненным циклом управляет Next.js или хостинг. Нужна диагностика отказов интеграций по статусу и длительности без записи ключей и подписей.
- Производственная сборка пригодна для локального старта. В репозитории нет гарантий прохождения проверок перед деплоем, проверки env по типам или описанного отката. Управляемые настройки Vercel, rate limits, CDN, Preview и фактическая production-версия не проверялись.

## 7. Приоритетный план

1. **Сразу:** решить судьбу зашитого ключа у OpenWeather, проверить квоту и синхронизировать локальный Next с lockfile. Сверить версию в разрешённой preview/production среде отдельно.
2. **Следующий релиз:** исправить SW и проверить переход со старого кэша. Изолировать отказы погоды, исправить интервал после выбора города и адаптивность на 320–430 px. Поднять работающий lint и базовый CI.
3. **Затем:** укрепить webhook и погодный API, ввести прогнозируемый fallback Cloudinary, покрыть API и ротацию тестами. Измерить объём передачи и задержки на нескольких размерах каталога и при повторной загрузке.
4. **После измерений:** ограничить payload каталога и пагинировать длинные списки, если бюджет передачи или DOM этого требует. Отдельно разобрать статическое наследие, доступность, PWA-иконки и документацию. Сохранить редиректы старых URL.

### Минимальный набор регрессий

- Колода: пустой и малый каталог, переход через конец колоды, дубли среди видимых, пауза при скрытой вкладке и модальном окне.
- Weather: пустой/валидный ввод, отсутствие ключа, 429, таймаут, невалидный JSON, быстрый выбор двух городов и новое значение через интервал.
- Webhook: корректная подпись, просроченное событие, неверная папка, malformed payload, повтор валидного события. Проверять с тестовым ключом.
- Browser: 320/375 px и desktop, клавиатура, reduced motion, просмотр и скачивание с тестового origin, reload после обновления SW, offline и восстановление, OG/favicon и старые редиректы.

## 8. Границы аудита

- Production, Vercel API, Cloudinary и OpenWeather не вызывались. Из внешних источников использованы реестр npm и публичная документация Next.js. Секреты и квоты поставщиков не проверялись.
- HTTP и браузерные проверки проводились локально с зафиксированной версией Next.js. Chrome проверен на одном мобильном размере с заблокированными внешними хостами. Firefox/Safari, полноформатный аудит доступности, реальная установка PWA, кэш между релизами, доставка CDN и пользовательские метрики не проверялись.
- Проверки безопасности пассивные. Нет утверждения о полном отсутствии уязвимостей или секретов. Нет БД, пользовательских аккаунтов, контейнеров и наблюдаемого CI в репозитории. Их оценка неприменима либо ограничена настройками хостинга за пределами проекта.
